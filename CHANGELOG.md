## [Unreleased]

### Added
- Documentation scaffolding: **30 documents** — 26 under `docs/` plus root-level README, CHANGELOG, CONTRIBUTING and PROJECT (the PRD), alongside LICENSE. (Began as 28; `SECURITY_INVARIANTS.md` and `GLOSSARY.md` were added as the work found the need for them.)
- `requirements.txt` / `requirements-dev.txt` pinned to versions verified against PyPI for Python 3.12.
- `.python-version` pinning the interpreter to 3.12.
- `pyproject.toml`: ruff, mypy (strict on `src/`), pytest markers, coverage floor.
- **Provider-agnostic LLM access.** `LLMClient` protocol in `src/core/ports/`, with a fake adapter and a factory. One OpenAI-compatible adapter is planned to cover Groq, Gemini, OpenRouter, Ollama and LM Studio via `base_url`. See ADR-014, which supersedes ADR-009.
- **Typed settings validated at startup** (`src/core/settings.py`), including an SSRF guard on `LLM_BASE_URL` that resolves the host and rejects link-local, private, reserved and multicast addresses.
- **PostgreSQL 16 + pgvector**, Alembic migrations, and the `agent_meta` schema: `schema_elements`, `foreign_keys`, `sessions`, `session_turns`, `query_audit`, with an HNSW index for ANN retrieval.
- **The read-only role** — `SELECT`-only, no privileges on `agent_meta`, with role-level `statement_timeout`, `idle_in_transaction_session_timeout`, `work_mem` and `default_transaction_read_only`.
- **The schema catalog** — introspection of tables, columns, types, comments and foreign keys from `pg_catalog`; serialization to the text that gets embedded; an `Embedder` port with a sentence-transformer adapter and a dependency-free hashing adapter; and an idempotent, single-transaction indexer. `assert_catalog_ready` refuses startup when the configured retriever has no vectors indexed.
- **Schema retrieval** — `SchemaRetriever` ranks catalog elements against a question over pgvector ANN, returns the foreign-key edges connecting the tables it matched, and supports `table_filter`. `k` is clamped to the ceiling published in the `schema_search` tool schema, and `RETRIEVAL_TOP_K` / `HNSW_EF_SEARCH` are configurable.
- **SQL validation** — five stages, cheapest first: sqlglot parse, single-statement, read-only, identifier resolution against the catalog with nearest-match suggestions, then `EXPLAIN` with a cost ceiling. Stages 1–4 perform no I/O and are callable on their own, so obviously bad SQL is still rejected when the database is unreachable.
- **Sandboxed execution** — `SQLExecutor` re-validates every query rather than assuming `validate_sql` ran, injects the row limit into the AST (smaller-wins, clamped to a ceiling the caller cannot raise), sets `statement_timeout` per statement, and returns a `truncated` flag that distinguishes a server-imposed cut from the caller's own `LIMIT`. Every attempt is audited over a separate owner connection; result values are never stored.
- **SQL generation** — the OpenAI-compatible adapter (one class for Groq, OpenRouter, Cerebras, Gemini's compatibility endpoint, Ollama and LM Studio, differing by `base_url`), a `sql_gen` prompt that states the dialect and orders itself longest-stable-prefix-first for caching, and a generator that repairs the markdown fences models emit by habit. `CANNOT_ANSWER` is a distinct failure from a bad query, because retrieving more schema helps and retrying generation does not.
- **Provider agility** — `LLM_MODEL_FALLBACKS` gives an ordered model chain that advances on a 429, so a spent per-model daily cap becomes a logged switch rather than a failed run. `python -m generation.check` verifies a provider with one round trip before anything depends on it.
- **Table profiling** — `TableProfiler` returns null fraction, distinct count, extremes and frequent values so the agent can tell two plausible columns apart, or learn that a column stores `'FI'` rather than `'Finland'`. It is the only component whose output is row-derived by design, so every bound on it is a disclosure control: identifiers are resolved against the catalog before any statement is composed, a value must clear a frequency threshold before it may be reported, extremes are returned only for numeric and temporal types, and raw cells require `PROFILE_ALLOW_VALUE_SAMPLING`, which is off and cannot be opened by a caller. Anything withheld is reported as withheld, with the reason. See ADR-016.
- **The four MCP servers**, each an independent process over stdio: `search_schema`, `validate_sql`, `execute_sql`, `profile_table`. Each is a thin adapter over a component that was built and tested without any knowledge of MCP — every bound lives in the component, because another host can connect to one server alone. Published ceilings are imported from the code that clamps them, so what a caller is told and what is enforced cannot drift. Tool descriptions state *when* to call, not just what, and are treated as prompts. See ADR-017 and MCP.md.
- **Runtime tool discovery.** `ToolRegistry` connects to the configured servers, calls `tools/list`, and builds its capability set from the answers — no hardcoded tool list, and a server that fails to start costs a capability rather than the session.
- **Copy-pasteable host configuration** (MCP.md §9), with the four setup mistakes that produce confusing failures. Three ways to drive the servers, none of which costs anything or needs an account: the project's own `ToolRegistry`, the open-source MCP Inspector via `npx`, and any stdio-speaking desktop host — listed in that order deliberately, since a core capability should not be contingent on one vendor's product decisions.
- **The eval harness** — result-set comparison implementing every rule in EVALUATION.md §1.1, Recall@k over schema elements extracted from the reference SQL, a failure taxonomy that classifies by earliest cause, per-question artifacts, and **resumable runs**. Resumption is the design constraint rather than a convenience: free-tier models cap tokens per model per day, so being stopped partway through a run is routine, and a resume whose configuration differs is refused rather than silently averaged. `python -m evals.run` runs the pipeline; see the seam entry below.
- **Benchmark loading** — `python -m benchmark.load` acquires an archive, converts SQLite to PostgreSQL one schema per database, verifies the conversion, and assigns database-level splits. Every gold query is executed on both engines and compared with the eval harness's *own* comparator, because the question is not whether the two databases are identical but whether the eval will score a correct answer as correct (ADR-022); the command exits 3 when a database fails, so CI cannot pass while reporting the data is wrong. Types are inferred from the data rather than the declaration, since SQLite does not enforce one. Identifiers are folded to lower case so unquoted gold SQL resolves, and an unrepresentable name refuses the database instead of being rewritten into a silent collision (ADR-019). Splits are a hash of the database name, not a seeded shuffle, so adding databases never moves the ones already assigned (ADR-021).
- **Spider 1.0 is loaded, converted and verified.** 20 dev databases into PostgreSQL, and **915 of 921 comparable gold results reproduced — 99.3% conversion fidelity**, with 19 of 20 databases reproducing every one. The archive is pinned at `sha256:00636695…c85b121b` in `data/artifacts.lock.json`, and the database-to-split assignment for all 160 databases is committed. Recorded in [BENCHMARKS.md](docs/ml/BENCHMARKS.md) §0, which every later accuracy row inherits — a system score measured on a converted database is bounded by how faithfully that database converted. The 25 remaining mismatches are stated, not rounded away.
- **The pipeline is wired into the answerer seam** — `evals.pipeline` composes retrieval, generation and validation into an answerer, and `evals.run --baseline` selects between the three EVALUATION.md §4 configurations that exist today: `full-schema`, `retrieval-only`, `with-validation`. It was never one line, and the three reasons are the slice. A benchmark is 20 databases while every component was written for one, so a `DatabaseScope` is resolved per question and the catalog namespace *is* the PostgreSQL schema name — one name rather than two that could disagree (ADR-031). Gold SQL is the statement `benchmark.load verify --emit-gold` recorded, never one re-derived at run time, because verification's claim is that *those results were compared* and re-transpiling silently drops the claim (ADR-030). And the eval's query runner is deliberately not `SQLExecutor`: injecting a row limit into both sides of a comparison cuts two unordered result sets in different places and reports a correct answer as a value mismatch (ADR-032).
- **The eval's denominator is the verification's `comparable` set**, defined once. Conversion fidelity is *matched / comparable*; execution accuracy will be measured over exactly the questions `comparable` counts — **921 of Spider dev's 1034**. The 113 excluded are reported by outcome in every run summary, and a question the verifier never saw stops the run rather than being scored or dropped.
- **`python -m benchmark.load index`** — builds the schema catalog for every converted database, introspecting as the read-only role so a table the agent cannot `SELECT` is never catalogued. Separate from `convert` because re-indexing after a retriever change must not re-convert the archive.

First measured execution accuracy: **75.3%** over 150 of 921 scoreable questions, which is **3 of 20 databases** and therefore a smoke sample rather than a benchmark result. [BENCHMARKS.md](docs/ml/BENCHMARKS.md) §1 states that bound on every row, along with the two others that stop any of it being comparable to a published Spider number.
- **The full-split run is under way, and the first thing it did was overturn the smoke rows.** 379 of 921 questions and **9 of 20 databases** answered by a single model before the free tier's daily cap halted it; the run resumes into the same directory rather than restarting. **80.9% execution accuracy** ([BENCHMARKS.md](docs/ml/BENCHMARKS.md) §1.1), against 72.7% from the 150-question sample — and the reason it moved is the finding. `car_1` scores **55.4%**, the worst of the nine, and it is one of the three databases every smoke row was made of. Those rows were not a small random sample; they were weighted toward the hardest database in the corpus. The per-database spread is **55.4% to 97.1%**, which describes the system better than any single figure over a partial one.
  - **`cre_Doc_Template_Mgt` scored for the first time: 67/74, 90.5%** — the 84 questions that were `scope_unavailable` yesterday, now the second-strongest database in the run.
  - **The halt and the resume were verified on real data, not only in tests.** The cap arrived at question 414; ten consecutive `llm_failed` tripped `--halt-after` and the run stopped with **542 questions untouched** rather than recorded as failures. `resume()` on that directory reports *367 answered, 12 to re-attempt*. The equivalent run a day earlier recorded 308 permanent failures and could never be finished.
  - **Recall improved with coverage and the ceiling did not move**: R@1 0.605 → **0.687**, R@5 0.889 → **0.936**, R@10 0.960 → **0.982**, R@20 **1.000 → 1.000**. A ceiling that survives 2.5× the questions and 3× the databases is a property of the corpus rather than an artefact of a small sample, which strengthens the case for BIRD over Spider for the Stage 5 fine-tune.
  - **Invalid-query rate is 3.3%, up from 2.7%, and that is not a regression** — the same code over 367 scored questions instead of 150. Recorded at the higher figure because the number Stage 4 must beat has to come from the widest sample available.
- **The first runs found seven defects, two of them worth thirty accuracy points each.** `RETRIEVAL_TOP_K` defaults to 10 and a Spider database holds 10–67 catalog elements, so the model was shown a partial schema and honestly refused half the questions — 42.7% at k=10, 72.7% at k=30, with Recall@20 at 1.0. And a reasoning model's `<think>` block was being submitted to the database as SQL, costing 27 of 150 questions with correct SQL sitting after the closing tag. That one was invisible while the configured model answered every question; it appeared only when a rate limit moved the fallback chain to a model that emits reasoning in `content`.
- **A run can be a blend of models, and now says so.** The free tier's daily cap advances `LLM_MODEL_FALLBACKS` mid-run. One measured run was 96% for one model and 59% for another, reported as 75.3% — a number neither earned. `answered_by` and `single_model` travel with every summary and the CLI warns.
- **Four of the runner's own error types had no failure category** and were landing in `uncategorised`, a bucket meaning "nobody could explain this". `execution_failed` became its own category; `llm_failed`, `scope_unavailable`, `retrieval_failed` and `internal_error` became `infrastructure` and **leave the scored denominator**, for the reason gold errors do — counting a ten-minute rate limit as wrong answers reports it as a model that got worse.
- **Baseline schema-linking recall**, the number Stage 5 must beat: R@1 0.687, R@5 0.936, R@10 0.982, **R@20 1.000** on Spider dev, over 379 questions and 9 databases. (The earlier 150-question sample gave R@5 0.889; R@20 held at 1.000 across both.) Full coverage by rank 20 bounds what a fine-tune can buy *here*, which is the argument for BIRD and is the null result [R-01](docs/project/RISKS.md) predicted the shape of.
- **Test suite: 1364 tests** — 912 unit, 189 integration against a real Postgres via testcontainers, 257 security, 70 contract (layers overlap: a security test needing a database is both). The security suite is negative: it passes when the database refuses. The contract suite launches the servers as real subprocesses and talks to them over real stdio.
- **Layer markers are derived from the directory**, not declared per module. Thirteen files had drifted without one — including `tests/security/test_benchmark_acquisition.py` and `test_dsn_handling.py`, both release-gate suites — and an unmarked test is *deselected* by `pytest -m security` rather than skipped, so it is reported by nothing at all. The gate was running **156 of 206** security tests and had no way to say so. A test outside the known layers now fails collection.
- **Configuration completeness is now asserted rather than reviewed.** `tests/unit/test_settings.py` enumerates every field on every settings class and fails if one is missing from `.env.example` or CONFIG.md. Added after an audit found 18 of 50 settings had reached the code without reaching the template — a drift [R-17](docs/project/RISKS.md) predicted and nothing could detect.
- **The scale and concurrency path is written down** ([FUTURE.md](docs/project/FUTURE.md)), because everything in v1 is bounded for a *single caller* and that is a consequence of the deployment model rather than an oversight. Covers the connection pool the `ConnectionSource` seam is waiting for, two-tier interactive/batch execution routed by the `EXPLAIN` cost already computed and currently discarded, per-user admission control, role-level resource limits, and tenant-aware retrieval. Also records why per-machine installation is the wrong shape: it distributes the credentials the entire containment argument rests on.
- **`POST /v1/query` is served, and the project answers a question over HTTP for the first time.** Non-streaming: question in, generated SQL and rows out, under a row limit injected into the AST and a statement timeout. Verified against a real Spider schema — *"How many singers are there?"* → `SELECT COUNT(*) FROM singer;` → `6`, and a `max_rows: 3` request returned three rows with `truncated: true`. The six controls [SECURITY.md](docs/operations/SECURITY.md) §13.9 named as prerequisites landed with it rather than after it.
  - **A request body cap enforced before parsing**, as pure ASGI middleware. `Content-Length` is checked first as the cheap rejection and is **not trusted** — received bytes are counted as they arrive, because the request that matters is the one that understates the header or omits it entirely under chunked encoding. Checking only the header is a limit any caller can opt out of.
  - **A real connection pool**, and it is not a performance change. `statement_timeout` is set per transaction, so two concurrent requests sharing one connection would run one under the other's limit. Every pooled connection is proved by `assert_read_only` as the pool opens it, not just the first — ADR-033 is about the connection a request actually uses.
  - **Blocking work moved off the event loop** — execution, validation *and retrieval*. The last was a defect found in this slice: `QuestionAnswerer.candidate()` was `async` and called a synchronous pgvector query inline. It was harmless for as long as its only caller was the eval harness, which is sequential. [ADR-036](docs/architecture/DECISIONS.md) recorded the risk of building that seam one commit before its second caller; this is what the risk cost.
  - **A validation failure is no longer a schema-enumeration oracle.** `SQLValidationError` names the offending identifier *and the catalog's nearest match* — written for an operator holding the schema, and over an unauthenticated endpoint it completes an attacker's guesses rather than merely confirming them. The response now names the category only; the detail goes to the log and the audit trail under the same `request_id`. SECURITY.md §13.10.
  - **Unimplemented fields are refused by name, not accepted and ignored** ([ADR-038](docs/architecture/DECISIONS.md)). `stream` and `session_id` produce a `400` naming the field, and the response omits `answer` rather than sending an empty string. Same defect as a config variable nothing reads, one layer out — and `session_id` is the sharp case, because silently dropping it answers a follow-up without the previous turn's context and returns something *plausible*.
  - **Two controls are honestly partial.** The in-flight cap is process-wide rather than per client, and the oracle defence leaves a timing channel. Both need to know who is calling, so both wait on authentication; §13.9 says so in the table rather than in a footnote.
- **A demo UI, and Stage 1's core loop is now something a person can watch.** Vite + React + TypeScript under `web/`, consuming `POST /v1/query` over SSE. Verified in Chrome on 2026-08-08 against a real Spider schema: question in, highlighted SQL and rows out, with each phase drawn against a real time axis as the events arrive. Served by FastAPI behind `API_STATIC_DIR`, or by the Vite dev server locally. 112 tests, strict `tsc` with `noUncheckedIndexedAccess`.
  - **The rail is a time axis, not a progress bar**, and that is the whole design. A stepper with four checkmarks says the same thing whether a phase took 12 ms or 20 s — which is exactly how a twenty-second model checkpoint load stayed invisible long enough to be written up as a rate-limited provider. Segment lengths are square-root compressed, because linear would make a 12 ms execution one pixel next to a 20 s retrieval; the axis says it is compressed and every segment carries its real duration.
  - **Two clocks, both shown, neither substituted for the other** ([ADR-044](docs/architecture/DECISIONS.md#adr-044--two-clocks-both-reported-neither-substituted-for-the-other)). The rail is what the browser observed, network included; the footer is what the server measured inside itself. They do not even report the same phases — the stream announces `retrieve`/`generate`/`execute` while `steps[]` reports `answer`/`execute` — so merging them would produce a number that is neither.
  - **The client frames the SSE stream itself** ([ADR-041](docs/architecture/DECISIONS.md#adr-041--the-ui-frames-the-sse-stream-itself-because-eventsource-cannot-post)). `EventSource` issues `GET` only, so using it would mean putting the question in a URL — logged by every intermediary on the path and kept in browser history. The parser handles chunk boundaries falling anywhere (a `\r` at the end of a chunk is *held*, since its `\n` may be in the next one) and bounds both a single line and one event's accumulated data. Both bounds are **refusals, not truncations**: a truncated event handed on as complete is worse than an error.
  - **Nothing renders markup** ([ADR-042](docs/architecture/DECISIONS.md#adr-042--syntax-highlighting-returns-tokens-never-markup)). The page displays SQL a model wrote from a stranger's question, and row values from whatever database the operator pointed at. Every syntax highlighter worth using returns a string of HTML, which needs `dangerouslySetInnerHTML`; this one is a hand-written scanner returning tokens the component turns into elements. `dangerouslySetInnerHTML` appears nowhere in `web/`. The scanner is a scanner rather than a regex because it cannot backtrack — the obvious pattern for a quoted string with escapes is the catastrophic-backtracking shape, and a test feeds it 50,000 doubled quotes.
  - **The two truncations are reported separately.** The server clipping a result set and the browser showing fewer rows than it received are different facts; one banner covering both would let a reader take the wrong one away. A `rows` event arriving without its `truncated` flag is **rejected rather than defaulted to `false`** — a default there is the client asserting completeness the server never claimed.
  - **Served from the API's own origin, which keeps `API_CORS_ORIGINS` empty.** With no authentication, every entry in that allowlist would be an origin allowed to drive the endpoint from a visitor's browser. Same-origin means none is needed; the Vite dev server preserves the property by proxying rather than by being allowlisted. The cost is stated in SECURITY.md §13.15 rather than assumed away.
  - **`API_STATIC_DIR` is off by default** and refuses to start when set to a path that is missing, is not a directory, or holds no `index.html` — the last being what an interrupted build leaves behind, which would otherwise serve 404s from a process reporting itself healthy.
- **Security headers on every response.** `SecurityHeadersMiddleware` sets a Content-Security-Policy (`script-src 'self'`, no `unsafe-inline`, `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'none'`), `X-Content-Type-Options: nosniff`, `X-Frame-Options` and `Referrer-Policy`. Registered last so it is the **outermost** middleware: a request refused by the body cap never reaches a route, and a header applied only where a route was reached is applied where it was needed least. The CSP holds `script-src 'self'` only because the Vite build inlines nothing (`assetsInlineLimit: 0`) — a build option that can silently weaken a security header, so both carry a comment saying so. SECURITY.md §13.13.
- **The full Spider dev split is measured: 921 of 921 scoreable questions, all 20 databases, 79.9% execution accuracy, single model, zero infrastructure errors** ([BENCHMARKS.md §1.1](docs/ml/BENCHMARKS.md)). Three days and three free-tier daily budgets, resuming into the same directory each time. §5 latency and §6 cost now carry measured rows too — p50 3.09 s / p95 7.62 s per question, and $0.00 at 494 in / 183 out tokens.
  - **The number went down when the run finished, and that is the finding.** 81.4% at 744 questions became 79.9% at 921. The remaining 177 were not a random sample — they were whatever the walk had not reached. **A partial run is a biased sample of its own corpus and the direction of the bias is unknowable until it completes**, which is why the earlier figure is superseded rather than quoted anywhere.
  - **The regression log gained three entries, all "sample, not code".** Execution accuracy, R@20 and R@1 all moved down between dated rows with one commit answering every question. A log that only records code regressions cannot explain the drops measurement itself produces — and those are the ones most likely to be quietly replaced with the flattering earlier figure.
  - **Resumption paid for itself.** Days 1 and 2 each ended with 12 questions failed against a spent quota; day 3 re-attempted rather than retired them and all 12 succeeded, so `scored` equals `total` for the first time. Without it this corpus was not measurable on a free tier at all.
  - **R@20 was never a ceiling.** It read exactly 1.000 over 150 questions and again over 379, then fell at every widening: 0.9983 at 744, **0.9973** at 921. A metric at its maximum has no visible variance, so repeated agreement looks identical to a sample that is simply too small. §2 keeps the superseded reasoning verbatim.
  - **Two things it does not measure, stated on the row.** It is `retrieval-only`, so no validator ran and `validation_attempts` is 0 on all 921 artifacts *by construction* — self-correction has no number. And it runs the direct answering path, so **no accuracy figure measures the MCP servers**. (The second half of that sentence read *"proven to answer as well by nothing"* until 2026-08-11, when the `mcp-retrieval` baseline measured the retrieval hop identical over all 1,034 dev questions — see the MCP baseline entry below. The accuracy figure is still a direct-path measurement.)
- **SSE streaming is served.** `POST /v1/query` with `stream: true` reports progress as it happens: a `stage` event per completed phase, then `sql`, `rows` and a terminal `done`. Verified live against a real Spider schema, with the SQL visible before the rows arrive.
  - **Only the events that have something behind them.** `stage`, `sql`, `rows`, `done`, `error`. API.md also specifies `session`, `plan`, `tool_call`, `tool_result` and `answer_delta`; none is emitted, because an event with fabricated contents is the accepted-and-ignored field wearing an event name — and `session` is the sharp one, since its specified payload is an id for memory that does not exist. `stage` is an addition to that list, and it is the one carrying the progress.
  - **`stream` is now a real request field.** It was refused by name for exactly as long as there was no stream behind it. That is [ADR-038](docs/architecture/DECISIONS.md#adr-038--the-served-request-accepts-only-fields-that-do-something) running forwards: a field appears when its behaviour does. `session_id` is still refused.
  - **A stream is admitted before it is a stream** ([ADR-039](docs/architecture/DECISIONS.md#adr-039--a-stream-is-admitted-before-it-is-a-stream)). Once a `200` and its headers are sent, a `429` is no longer expressible — so `QueryService.stream()` is deliberately **not** `async`: an async generator's body does not run until the first `__anext__`, by which point the route has already returned. Admission is a synchronous counter shared by both response shapes, atomic against the event loop because there is no suspension point between the test and the increment.
  - **A disconnected client cannot hold a slot.** The release is in the generator's `finally`, so it runs on completion, on failure, and when the client hangs up. Releasing only on success would let four abandoned connections take the endpoint out until restart, at a cost to the attacker of four sockets. SECURITY.md §13.12.
  - **Payloads cannot forge events.** SSE is newline-delimited, so a raw newline in a `data:` line does not corrupt the frame — it *ends* it, and the rest is parsed as a new event. **Generated SQL is routinely multi-line**, so this is the ordinary case rather than an attack, and the attack is a question crafted to make the model emit `

event: done`. Every payload is a mapping serialised by `json.dumps`; event names are validated too, because a name gets its own line. SECURITY.md §13.11.
  - **One error rendering, not two.** A stream cannot use the exception handlers — its response has already begun — so it renders failures itself, through the one `errors.published` function that decides which of this project's messages a caller may read. Two renderers, one rule: the alternative is a strict copy and a lenient copy in one process.
- **Startup opens the retriever's model, and the first request stopped costing twenty seconds** ([ADR-040](docs/architecture/DECISIONS.md#adr-040--startup-opens-the-model-because-naming-it-is-not-loading-it)). The lifespan promised eager initialisation and read `retriever.model_version` — a configured *string* that loads nothing — while `SentenceTransformerEmbedder` held its checkpoint closed until the first `embed()`. So the process logged `ready` over an unloaded model, a corrupt checkpoint would have surfaced on the first request rather than at startup, and whoever asked first paid the load. It now reads `retriever.dimensions`, which cannot be answered without opening the file.
  - **Found by the instrumentation, not by reading the code.** The per-stage events split `answer` into `retrieve` and `generate`, and the first streamed request showed retrieval at twenty seconds against generation's two. **This corrected a benchmark**: PERFORMANCE.md had recorded 29 s as the cost of a rate-limited provider, on the strength of an aggregate that could not tell the two apart. Measured after the fix: **first request 2.9 s, warm 0.6–1.8 s, `execute` 15–21 ms** — the `< 8 s` budget is met, and the earlier "missed by 3.6x" was measuring process startup.
- **The HTTP API's foundation** — `create_app()`, `GET /health`, `GET /ready`, the sanitized error envelope, and request correlation. This is the project's first surface reachable by someone who does not already have the machine, so the slice is mostly the controls that follow from that. Reviewed in full at [SECURITY.md §13](docs/operations/SECURITY.md).
  - **`/health` checks nothing but that the process is running**, and a test fails if it issues a query. A liveness probe that touched the database would fail every replica at once during a blip, and the orchestrator would answer a recoverable incident by restarting the fleet.
  - **`/ready` reports two fixed words per dependency and never the reason.** A driver message carries the DSN, the internal hostname and the role name, and the endpoint is unauthenticated because a kubelet cannot hold a credential. The verdict is cached for 5s so being probed does not scale with probe frequency, and an unconfigured checker answers *not ready* — `all([])` is `True`, so the naive version says yes during startup.
  - **The error envelope covers the three paths no route author writes**: an unrouted 404, a framework validation failure, and an unhandled exception. A message from `core.exceptions` was written for a caller and passes through; anything else becomes one fixed string, identical for every cause so it cannot be read as an oracle. The same bug one layer down is why `mcp_servers.common` exists — there the leak went to a model on the operator's machine, here it would go to whoever sent the request.
  - **`X-Request-Id` is honoured but not trusted.** An allowlist-matched value is repeated so a gateway's trace survives the hop; anything else is *replaced*, not rejected. A newline in that header writes a second log line the attacker chose (CWE-117). The pattern is anchored `\A`/`\Z` rather than `^`/`$`, because Python's `$` also matches before a trailing newline — which is exactly the input it exists to reject.
- **Closed-by-default API configuration, enforced as validators rather than defaults.** A non-loopback `API_HOST` and a `*` CORS origin are both **startup errors**. CONFIG.md has specified the first since Stage 0, conditioned on an `API_KEY` that does not exist yet; the honest form today is stricter, because there is no authentication at all and a service that started successfully produces no warning anyone reads. All four spellings of loopback are accepted, so nobody has to work around the control to run a legitimate configuration. `API_DOCS_ENABLED` is off and governs `/openapi.json` as well as `/docs` — clearing only `docs_url` hides the page and leaves the machine-readable route map served.
- **A composition root** (`src/composition/`). `Resources` moved out of `mcp_servers/`, where the HTTP API would have had to reach into a sibling entrypoint's package to open a database connection. Both are adapters over the same components and neither may depend on the other.

### Fixed
- **Resumption retired questions the model was never asked, so a spent token budget still lost the run.** The artifact store's whole reason for existing is that a free-tier daily cap arriving mid-run should cost nothing — every question is written as it completes and a re-run skips what is on disk. But `resume()` returned every recorded id without asking *why* it was recorded. The first full-split attempt hit the cap at question ~395 of 1034 and wrote 308 `llm_failed` records; each was thereafter permanently done. The run could not be finished by resuming, only restarted from nothing, and the next day's budget would have stopped in the same place. **A budget spent failing was still a lost run — it just looked like a completed one.** Resumption now skips what was *answered*: an artifact whose `error_type` says the system under test never got to answer is re-attempted, overwriting its record. ([ADR-037](docs/architecture/DECISIONS.md#adr-037--resumption-skips-answered-questions-not-recorded-ones))
  - **The set that decides this already existed**, doing the same job under another name. `FailureCategory.INFRASTRUCTURE` means *the model was never asked*, which is why those questions leave the scored denominator — and it is the same reason they must be retried. Both now read one predicate, and a test asserts the two agree. `unanswerable` and `execution_failed` are deliberately **not** retried: those are things the run learned, and re-asking them spends budget re-deriving results already in hand.
  - **A run now stops at a wall.** Ten consecutive infrastructure failures end it (`--halt-after`, `0` disables). A spent budget does not recover mid-run, so continuing means asking a dead provider once per remaining question — the previous attempt did that 308 times, burying the cause under identical records. Consecutive rather than total, so a blip the provider recovers from does not stop a run making progress. The threshold is low enough to trip on a whole database failing as `scope_unavailable`, which is a deployment fault worth stopping for rather than scoring around — as the same run did with 84 questions.
- **The eval named one database's schema differently from the loader, and lost 84 questions to it.** `ScopeRegistry._dataset_for` concatenated prefix and `db_id` directly; `benchmark.convert.schema_name_for` does the same concatenation and then folds the result to lower case ([ADR-019](docs/architecture/DECISIONS.md)). The two therefore agreed for every already-lower-case `db_id` and disagreed for the one that was not — Spider dev's `cre_Doc_Template_Mgt`. The loader created `spider_cre_doc_template_mgt`; the eval asked for `spider_cre_Doc_Template_Mgt` and got `scope_unavailable`. **That is an infrastructure error, so those questions leave the scored denominator** — the run reported a clean accuracy over 9% fewer questions than it claimed to cover, and said nothing about it. Its own docstring had warned against exactly this: *"One name, not two … inventing a second naming scheme for the catalog would create exactly one bug."* It then computed the name a second time. Now calls the loader's function.
  - **The 3-database smoke sample could not have found it.** `car_1`, `concert_singer` and `pets_1` are all lower case, as are both fixtures in the scoping integration tests. Every existing test passed for the same reason the bug survived. The new tests are unit-level and parametrized over mixed-case ids, plus one that asserts the *premise* — that the corpus still contains a mixed-case database — so the suite cannot quietly go back to only testing the easy case.
- **`.env.example` offered three variables nothing reads.** `LOG_LEVEL`, `LOG_FORMAT` and `LOG_RESULT_VALUES` sat uncommented, with values, while no code path read any of them — and CONFIG.md §7 correctly called them planned, so the two files disagreed in the direction that matters: the one operators actually edit implied the controls worked. **A dead setting is worse than a missing one** — a missing setting is invisible, a dead one is set, produces no error, and is concluded to have taken effect. `LOG_RESULT_VALUES=false` is why this is a security finding and not untidiness: it carried a comment describing what it protects, so a reader would conclude result logging was off *by policy*. It is off because the feature does not exist, which is a different fact and stops being true the moment somebody adds one. Planned settings are now named in that file in prose only, never as an assignment, so there is nothing to uncomment. A new test refuses any `NAME=` in the template that no settings class reads, with a five-entry allowlist naming what consumes each (`docker-compose.yml`, migration 002) and a second test that fails when an allowlist entry stops appearing — so the list cannot outlive its reason. This is the reverse of the check added last week, and it is the one the documentation audit identified as the only automatable part of itself.
- **`/ready` ran a blocking database call on the event loop.** Found by auditing the docs rather than the code: CODE_STYLE.md §6 rule 1 forbids sync `psycopg` inside `async def`, and the readiness route did exactly that. The reasoning that let it through was "`SELECT 1` is sub-millisecond and cached" — which is true in the healthy case and **fails on the case the probe exists for**. A write to a socket whose peer has gone away blocks until the OS gives up, so a probe whose job is to report an outage would, during one, stall the process it was reporting on. Now `await asyncio.to_thread(...)`. The rule it generalises to is in CODE_STYLE §6: *judge a blocking call by its behaviour in the failure it was written to detect, not by its cost in the healthy case.* The same treatment is a prerequisite for `POST /v1/query`, where the statement is a two-second aggregate rather than `SELECT 1`.

A reproducibility field that silently names a tree reproducing something else is worse than one reading `unknown`. Coercion failures now name database, table, column and value.
- **35 of 769 Spider foreign keys join two different types**, across 21 of 166 databases — `concert.Stadium_ID` is `TEXT` holding `'1'` against an `INT` holding `1`. SQLite joins them by applying numeric affinity to the text side; PostgreSQL answers `operator does not exist`. Both sides now take the numeric type where every value converts losslessly, and **never the reverse**: `'01' = 1` is true under affinity and `'01' = '1'` is false as text, so unifying toward text would compile and silently return fewer rows (ADR-025).
- **213 of 1034 verification failures were one SQLite quirk, misfiled against the conversion.** A double-quoted token matching no column is a *string literal* in SQLite, and the gold SQL leans on it (`WHERE course = "Math"`, `LIKE "%w%"`). The same schema-based test SQLite applies is now applied before transpiling — leaving alone any quoted token that is a real column, since Spider has names like `Official_ratings_(millions)`. Conversion faults went 213 → 0. PostgreSQL rejections are also split by SQLSTATE: a missing table or column blames the conversion, an undefined operator or grouping error is a dialect gap that would fail against a perfect conversion, and the second is counted and excluded rather than charged to the data (ADR-026).
- **16 verification mismatches were not mismatches.** `ORDER BY age` with tied ages leaves the order of the tied rows undetermined, and the two engines choose differently. Same query, same data, equal multisets — the order was never determined by the query. Recorded as `ambiguous_order` and counted as agreement, **in the verifier only**: `evals.comparison` compares two *different* queries, where a wrong order can be a real error, and relaxing it there would mark wrong answers correct (ADR-027).
- **SQLite's `LIKE` folds case and the transpilation did not say so.** `WHERE paragraph_text LIKE 'korea'` returns two rows on SQLite and none on PostgreSQL — silently different rows, not an error, which is why it surfaced as a conversion mismatch. `LIKE` now renders as `ILIKE` (ADR-026). Two details are load-bearing: sqlglot models `NOT LIKE` as a `Like` node carrying `negate=True`, so rebuilding it from its two obvious arguments **inverts the predicate** — caught by a test, and worse than the bug being fixed — and `ILIKE` folds by collation where SQLite folds only ASCII, which is recorded rather than closed. This also cost an existing integration test its premise: it had asserted `LIKE` case sensitivity was "a genuine engine difference", and it was a transpilation gap, misattributed exactly like the 213 quoted-literal failures. It now uses the one difference no transpilation can close.
- **16 mismatches were questions with no correct answer.** `SELECT hometown FROM teacher GROUP BY hometown ORDER BY count(*) DESC LIMIT 1` where three towns tie at the top: every engine returns *a* right answer and none need agree. Now `undetermined_limit`, counted and excluded from the denominator, since a question with no unique answer cannot be scored later either (ADR-029). **Detection requires two facts and the second one is the whole safeguard** — the un-limited results must agree *and* the `ORDER BY` key at the cut must be tied. 18 questions pass the first test; only 16 are ties. The other 2 are two engines ordering the same key differently, which is what a wrongly-typed column causes, so a one-fact rule would have relabelled a real conversion defect as benchmark ambiguity.
- **Diagnosing the 25 remaining verification mismatches raised fidelity from 97.3% to 99.3%**, and verified databases from 10 of 20 to **19 of 20**. Nothing about the conversion changed; the measurement got more accurate. The final 6 are one column — `wta_1.players.birth_date`, 20,144 integers and 518 empty strings — which has no faithful static type, and which DATASETS.md §3 predicted in writing before any archive was downloaded. Both BENCHMARKS.md §0 rows are kept, per the append-only rule.
- **The identifier allowlist refused two whole Spider databases** — `aircraft` over `%_Change_2007`, `orchestra` over `Official_ratings_(millions)`. Neither character can escape `sql.Identifier`, so the narrow set `[a-z0-9_ $-]` bought no safety and cost data. Now only a double quote, a backslash, a control character or a non-ASCII byte refuses a name. An allowlist doing usability work under a security label is worse than none, because its cost is charged to the security argument and nobody re-examines it (ADR-019).

### Security
- **Two security controls were correct by default and undiscoverable in practice.** `PROFILE_ALLOW_VALUE_SAMPLING` — the gate on returning raw row data to a third-party model — and `LLM_ALLOWED_HOSTS` — the SSRF host allowlist — were absent from `.env.example`. Nothing was misconfigured, which is precisely why nobody noticed: a safe default produces no symptom. **Severity Low, OWASP A05, confidentiality**, and the reasoning is recorded rather than the fix alone — a control an operator cannot find is one they cannot reason about, which is a weaker property than being correct by accident. Both are now in the template with the consequence of changing them, and the omission class is closed by an assertion rather than a review.
- **The schema catalog is a disclosure surface, and "add RLS" would not have covered it.** Row-level security and per-tenant roles constrain *execution*; `schema_search` answers from `schema_elements` before any query reaches the database, so a caller could learn that a table exists and what its columns are named without executing anything — and schema names are frequently sensitive on their own. Recorded in [SECURITY.md](docs/operations/SECURITY.md) §1 against the existing multi-tenancy limitation and as [FUTURE.md](docs/project/FUTURE.md) § *Tenant-aware retrieval*, because it is far cheaper to design into the catalog now than to retrofit as an authorization filter later. No change to v1, which is single-tenant.
- **The benchmark loader is the first untrusted *file* this project handles**, and it runs as the owner role — the widest privilege in the system applied to the least trustworthy input. Analysed in [SECURITY.md](docs/operations/SECURITY.md) §14.2.9. Archives are hashed against a committed lockfile *before* extraction, so a tampered file never reaches the zip parser (ADR-020); extraction refuses absolute paths, `..`, backslash separators, drive letters, symlinks and decompression bombs, validating the whole archive before writing a single byte so a rejection leaves nothing behind. Size caps are enforced against bytes *written*, never against the sizes the archive declares. SQLite sources are opened `mode=ro` with `trusted_schema=OFF`, views and virtual tables are skipped, and pragmas are parameterised via their table-valued forms. Converted schemas are granted `USAGE` + `SELECT` to the read-only role and nothing more, asserted by tests that check it still cannot write or create.
- Retrieval runs on the privileged owner connection by necessity, since the read-only role cannot see `agent_meta` at all. `src/schema/retrieval.py` is therefore held to static SQL and bound parameters only — no dynamic composition — and `table_filter` is bound as a `text[]` rather than built into the statement. Query text and returned elements are deliberately kept out of the search log. Written up as [SECURITY.md](docs/operations/SECURITY.md) §14.2.2.
- Documented and mitigated the exfiltration paths in [SECURITY.md](docs/operations/SECURITY.md) §14: SSRF via a configurable `base_url` (§14.1), and third-party exposure of row values (§14.2). The schema catalog path (§14.2.1) persists sampled values in a store that appears in no audit trail; §14.2.5 enumerates what actually crosses the network boundary and pins it by test. Schema value sampling defaults to **off**.
- **The MCP layer is a transport with its own failure modes**, analysed in [SECURITY.md](docs/operations/SECURITY.md) §14.2.7. Over stdio, stdout *is* the JSON-RPC channel, so each server hands the real stream to the transport and repoints `sys.stdout` at stderr — a stray `print` becomes noise rather than a killed session, and a startup traceback cannot put a connection string into the protocol stream. The MCP SDK's own catch-all returns `str(exc)`, which for a driver error can carry a password; the dispatcher therefore catches every exception first and lets only messages this project wrote reach the model.
- **A driver error message printed a live database password**, analysed in [SECURITY.md](docs/operations/SECURITY.md) §14.2.10 and rated **High**. psycopg quotes the connection string it was handed in its *parse* errors, and the handler rendered `str(exc)` — so a misconfiguration put the **owner** role's credential on the terminal, on the failure path, which is the path most likely to be screenshotted into an issue or shipped to a log aggregator. §9 of SECURITY.md had said "never in logs, traces, error responses" since Stage 0; nothing enforced it. `core/dsn.redact_dsn()` masks the password where the exception becomes a message (not where it is logged, so a second handler cannot bypass it), `raise … from None` closes the traceback path a redacted message alone leaves open, and the user name is deliberately left visible because "which role failed" is not the secret. A test asserts the **premise** — that psycopg really does quote the DSN — so if that ever changes, the redaction is known to have become belt-and-braces rather than load-bearing.
- **Archive extraction gained a second verdict, and briefly lost its first one.** An unrepresentable filename (Spider ships `receipts (3:11:18, 5:53 PM)_original.csv`) is a fact about the *filesystem*; an escaping member is a fact about the *archive*. The first is now skipped and recorded, the second still refuses everything — except an unrepresentable `.sqlite`, which refuses, because silently dropping a database changes the corpus every number is computed from (ADR-023). Written the wrong way round first: representability ran before the escape check, `..` is a component ending in a dot, and **a traversal attempt was being skipped as a portability problem**. The traversal suite went red on the same run. The ordering now carries a comment saying it is load-bearing, `.`/`..` are excluded as path semantics, and a regression test covers the intersection neither original suite did — because relaxing a security check to admit a benign case adds an edge the existing tests were not written to defend.
- **The split `.jsonl` files are no longer committed**, and were caught before they ever were. They hold the questions and gold SQL themselves — 2.5 MB of CC BY-SA content that would have been vendored into an MIT repo, against this project's own DATASETS.md §7. Only the database-to-split assignment is committed; the splits regenerate from it plus the archive the lockfile pins.
- **Profiling is the one path that deliberately sends row-derived values to a model**, and §14.2.6 analyses it in full — including the residual it does not close (a value that is both sensitive and common) and why regex PII redaction was rejected in favour of a frequency threshold (ADR-016): a filter that looks comprehensive changes operator behaviour, and is weakest exactly where people have stopped auditing.

### Added — testing and the MCP baseline

> **Recorded 2026-08-11, covering nine commits this file had not caught up with** (`651f35a`…`cd211fa`, 2026-08-09 to 2026-08-11). The gap is itself an R-17 occurrence and is logged as one in [RISKS.md](docs/project/RISKS.md). A changelog that skips the work between releases makes the release notes an archaeology exercise.

- **The MCP path is measured, and the answer is an identity rather than an accuracy** ([BENCHMARKS §8](docs/ml/BENCHMARKS.md), [ADR-045](docs/architecture/DECISIONS.md#adr-045--the-mcp-baseline-scopes-servers-by-process-because-the-tool-contract-has-no-dataset)). A fourth eval baseline, `mcp-retrieval`, routes the retrieval hop through `search_schema` on a real subprocess over stdio. All **1,034** Spider dev questions were asked both ways and the ordered element lists matched **1,034 times out of 1,034**, at a constant **+7.8 ms** median — 20 server starts for 20 databases, the pool bound working exactly. Until this landed, every published accuracy figure measured the direct path and the servers were proven to answer *as well* by nothing.
  - **The planned accuracy comparison was deliberately not run, and that is the decision worth reading.** A 100-question paired run is what a free tier affords in a day, and at ~80% accuracy it carries an interval near **±8 points** — wide enough to contain any regression worth finding. `PipelineAnswerer` composes retrieve → generate → execute from a single context source and the baseline swaps only that source, so identical context into identical code leaves nothing but provider nondeterminism: a measured gap would have been **sampling noise published as a finding about MCP**. The element comparison is exact, covers the whole corpus, and costs zero tokens.
  - **The tool contract has no `dataset` parameter and one was deliberately not added.** Scope travels in the process environment instead, at a cost of one server launch per database. Adding the argument would convert an operator-controlled scope into a model-chosen one — a prompt-injected question could name another tenant's catalog — and there is no authorisation tier to stop it. That parameter needs authentication to arrive first, not second.
  - **The baseline seam stopped branching per question.** `DatabaseScope` now carries the `ContextSource` its baseline resolved to, chosen once per database by a factory, so adding a fifth configuration extends a factory rather than editing a conditional every question passes through. An existing test had already ruled on this: `mcp-retrieval` retrieves *without* an in-process retriever, so it collided with `full-schema` on the old `(needs_retrieval, needs_validation)` pair while doing the opposite thing.
- **Property-based testing, in Python and in the browser.** 40 Python properties under the `property` marker (hypothesis, 100 examples locally and 500 in CI) and **15 more in `web/`** generated by `fast-check` on the same split. The Python set asserts that no generated write is ever accepted *and* no generated `SELECT` is ever refused — the half that stops a containment check being deleted the first time it blocks real work — that no payload forges a second server-sent event, and that `truncated` is true only when the server's limit did the cutting, checked against a reference model written independently of the executor. The browser set asserts the SSE parser's entire reason to exist: **where the chunks fall cannot change what comes out.**
  - The Python properties found a defect on their first run: `validate_static` caught sqlglot's `ParseError`, but `TokenError` is that class's **sibling**, not its subclass, and is what an unterminated string, identifier, comment or dollar-quote raises — the exact shape of a generation cut off by an output-token cap, which is the ordinary failure of the free tiers this project defaults to.
- **Failure injection — 38 tests that break each dependency on purpose.** Postgres dies and `/health` answers 200 while `/ready` answers 503, recovering on its own once it returns — tested down, up, and down again, because a health flag set once passes the recovery test and fails the second transition. The provider dies and exactly one terminal error is emitted, with no `rows` event and the next request served. The pool saturates and admission becomes a domain error rather than an internal one, audited even though nothing ran.
  - **One documented claim was false.** All four `__main__` modules promise, in identical words, that a bad `DATABASE_URL` kills the process while the host is starting it. `mcp_servers.schema_search` started cleanly against an unreachable database and exited 0.
- **The first concurrency tests, and the `locust` pin they replaced.** Every admission test this project had was shaped *"one caller holds the only slot, a second is refused"*, which proves the counter increments and nothing else. The new tests assert that callers at the cap all run **simultaneously** — a service that serialised everything satisfies the old tests, and only the in-flight peak tells them apart — that callers over the cap are refused rather than queued, that every slot returns after a burst of twenty and after a burst of failures, and that the executor never holds more connections at once than the cap allows. That last one is what makes the startup check `API_POOL_MAX_SIZE > MAX_CONCURRENT` mean anything. The tests were then mutated three ways to confirm they could fail. `locust` was pinned to write these and turned out not to be needed for them; it is removed.

### Fixed — testing and the MCP baseline

- **The error handler reflected the field name it was written to suppress.** `api.errors._fields` strips pydantic's `input` — the offending value — with a docstring explaining that a request body appearing in a response ends up in any log or error tracker that records responses. It then built the reported path with a plain join over `error["loc"]`, and with `extra="forbid"` on `QueryRequest` **the `loc` of an unknown field is the name the caller chose**. So `{"question": "hi", "<script>alert(1)</script>": 1}` came back as `{"field": "body.<script>alert(1)</script>"}` — the body reflected anyway, one level up, unbounded in length and unrestricted in content, on an unauthenticated surface. Found by reading the handler rather than by running the fuzzer.
- **A security property that had never failed, because its generator had never arrived.** `test_property_request_body.py` asserted that no generated body produces a 5xx. It failed for the first time on `{"question": "0"}` — and a `git worktree` at the untouched commit returned the same 500, proving the defect predated the change that reached it. **Two causes.** The shared fake retriever *raises* by design, a tripwire for API tests that should never reach the answering path; but this file's own docstring puts a valid body in scope, so an accepted body produced an `AssertionError` rendered as `500 internal_error` — the fixture manufactured the exact signature the test was hunting. And `status < 500` is a proxy that an honest, enveloped `502` breaks identically. The assertion now names what it means: any 5xx must carry a code other than `internal_error`. **Stricter than what it replaced on every rejected body, and correct on accepted ones.**
- **A sibling property failed on `<unn`** — a prefix of `<unnamed>`, the placeholder the application substitutes *because* the name was hostile. The response was right and the assertion was wrong, for the second time: it had already failed once on the single-character name `"` and been "fixed" with a length floor of four, which is where it failed again. Nine would fail too, because `<unnamed>` is a name a caller can send. **A length floor was never the fix.** The comparison now subtracts the application's own vocabulary, importing `api.errors.UNPRINTABLE_FIELD` rather than spelling it, and the found example is pinned as an ordinary example-based test beside the property — a property that finds a bug once and only re-finds it when the random stream cooperates is a regression test nobody has.
- **The eval pool double-counted server launches.** A cumulative per-client counter summed at eviction adds a reacquired client twice, so four launches reported six — and the overcount grew with the thrashing the number exists to report. **A derived metric whose sources are being discarded drifts in whichever direction the discarding goes.** Caught by the test written to pin the count.
- **The priorities table had gone stale about itself.** Rows 5 and 6 of the engineering matrix were still marked open after both landed, so anyone working the list top-down would have redone finished work. Completed rows are now struck through and kept rather than deleted, so the list reads as a record of what was worked and in what order.

### Security — testing and the MCP baseline

- **The retrieval server inherited the model provider's API key** — [SECURITY.md §10.3](docs/operations/SECURITY.md), **Low**, fixed in the change that found it. A subprocess inherits its parent's environment unless told otherwise, so the eval harness was handing `LLM_API_KEY` to `schema_search`, which embeds a question and queries pgvector and **never calls a model**. Nothing happens until something inside that process is compromised, at which point the key is one `os.environ` read away — and it is not a small process to be confident about: sentence-transformers, transformers, torch and psycopg all execute at import from a pinned graph this project did not write. **OWASP A05:2021, confidentiality only**; no integrity or availability impact.
  - **The fix is a denylist and that is the weaker control, stated rather than hidden.** Variables matching the five shapes secrets are named in (`API_KEY`, `SECRET`, `TOKEN`, `PASSWORD`, `CREDENTIAL`) are dropped; both database URLs are kept by name because the servers genuinely need them. An allowlist is stronger and was rejected on robustness — these subprocesses need `PATH`, `SystemRoot`, a model cache path, a TLS bundle and any proxy configuration, and an allowlist omitting one fails a run with an error naming none of them. **The residual risk is a secret in a variable matching none of the five patterns**, and it is written into SECURITY.md rather than left for a reader to notice.
  - Reviewed and found sound in the same pass: the `dataset` reaching a subprocess environment is validated as a PostgreSQL identifier before it gets there and reaches SQL only as a bound parameter; no shell is involved anywhere (`StdioServerParameters` is argv-based over a code-level module constant); start timeout, call timeout and pool size are all bounded, so a wedged subprocess costs one question rather than a run; and the row-value exclusion (`serialized`) is asserted to survive the wire against a real server.

### Fixed — the two guards Stage 5 would have needed and not had

> **2026-08-11.** Both were open items with an explicit "before Stage 5" note. Landing them found a defect that would have made a fine-tune's headline number meaningless, which is the argument for doing this kind of work *before* the stage that depends on it rather than during.

- **11 of Spider's 20 evaluation databases were in this project's own training split** ([ADR-047](docs/architecture/DECISIONS.md#adr-047--spiders-own-split-is-the-evaluation-boundary-and-the-training-set-is-carved-around-it)). Every accuracy and Recall figure published here is measured on Spider's official dev set. Hashing those twenty database names by [ADR-021](docs/architecture/DECISIONS.md#adr-021--splits-are-a-hash-of-the-database-name-not-a-seeded-shuffle)'s rule put **11 of them in `train`, carrying 605 questions**, and five more in `dev`/`smoke` — so 16 of the 20 sat in a band this project would have trained on or tuned against.
  - **The failure mode is why it needed a guard and not a note.** A Stage 5 fine-tune over that band would have fitted the retriever to 11 of the 20 schemas it is then scored on. That raises no error and produces no implausible number — it produces a **better Recall@k**, arriving exactly when a fine-tune is being evaluated for whether it improved Recall@k. The before, the after and the ablation would all have looked correct.
  - ADR-021's own tradeoff paragraph warned about the mirror image — *"a held-out set that quietly absorbed three training databases is not a split at all"* — and this arrived from the other direction: the **training** set absorbed the **evaluation** databases. Its *Revisit* clause named the fix in advance and had never been invoked.
  - **Fixed by reservation rather than by a new policy.** `assign()` takes a `reserved` set forced to held-out regardless of hash; `benchmark.load splits --reserve` supplies it from the benchmark's own question file, so there is no second copy of "Spider's dev databases" to go stale. ADR-021's stability property survives untouched, and a test asserts it: reserving one database may not move another. The split is regenerated — **98 train / 14 dev / 5 smoke / 49 held-out**, with zero overlap between the training bands and the evaluated twenty.
  - **`leaked_databases()` is now an executable check**, which is Stage 5's *"verify database-level split disjointness"* task landed early. It runs against the committed assignment, and a second test rebuilds the old assignment to prove the guard changes its verdict — so deleting the reservation and never regenerating cannot leave the suite green.
- **The resume guard hashed the commit, which was both too strict and too weak** ([ADR-046](docs/architecture/DECISIONS.md#adr-046--the-resume-guard-fingerprints-the-code-that-was-loaded-not-the-commit)). Too strict: the commit moves when a *document* moves, so days 2 and 3 of the three-day full-split run each had to be resumed from a detached `git worktree` — **an operational procedure invented to work around a guard firing on prose.** Too weak: the commit describes the repository the process *stands in*, while an editable install can import `src/` from a different checkout, so the guard could pass on precisely the run it exists to refuse.
  - `config_fingerprint` now hashes the source of the answering-path modules, read through each module's own `__file__`. A documentation commit resumes cleanly; a changed validator does not; a different checkout is a different digest.
  - **The module list is explicit rather than a walk of `sys.modules`**, because a walk is not deterministic — which modules are loaded depends on the configured provider and on import order, so two runs of one configuration could refuse each other. The staleness that a hand-maintained list would otherwise develop is checked *from the filesystem*: a test walks the answering packages and fails when a module is present in one and absent from the tuple, with every exclusion named and justified individually.
  - **Consequence, accepted deliberately:** every fingerprint changes, so no run recorded before this commit can be resumed. TASKS held this open with the note *"unblocked 2026-08-08; the run it would have orphaned is finished"* — landing it mid-run would have destroyed the run.
- **`retriever_model_version` defaulted to the empty string while sitting inside the fingerprint.** So the guard that stops a baseline run and a fine-tuned run resuming into each other was inert unless an operator remembered a flag — and every run made so far records the same empty value, meaning **it would first have been needed at the exact moment it was first useless.** It is now derived from the configured embedder, which is what `SchemaRetriever` binds into its `(dataset, model_version)` predicate and therefore the vector space a run actually reads. `--retriever` survives as an **assertion**: a value that disagrees with the embedder is refused rather than recorded.
- **One task was open in two stages** and would have been closed in one. Both entries for the `retriever_model_version` work are now closed and cross-referenced.
